Kafka Migration from MSK to Strimzi

Planned and ran the move of our Kafka clusters from Amazon MSK to Strimzi on our own Kubernetes clusters, with gzip as the cluster-wide compression since most producers already used it.

During the cutover, a few older applications that relied on lz4 started to fall behind. Instead of rolling back, I built a small transcoder so they could keep consuming, and the migration went ahead.

Cluster-wide changes now start with a compatibility check across every producer and consumer.

Incidents

Production Incidents

Issues I root-caused on call, and the fixes that followed.

01
PostgresLinux

PostgreSQL Connection Failures

Services across one cluster kept dropping their Postgres connections with "unexpected EOF", which pointed at the network. I traced it to the database host instead: strict memory overcommit with no swap left Postgres about 140 MB to start new connections. Fixed with one kernel setting and no restart.

PostgreSQLLinuxOKE
140 MB → 10 GBmemory headroom for new connections
02
KubernetesKafka

Kafka Consumer Lag Caused by VPA

A consumer group kept rebalancing and lag reached 20 million messages. VPA had cut the decoder pods from 500m to about 53m CPU, so batches ran past the poll timeout and the consumers were dropped from the group. I pinned CPU at 200m and moved VPA to recommendation-only mode.

VPAKEDAKafka
20Mmessages of lag
53m → 200mCPU per pod
03
MQTT

EMQX Cluster Cold-Start Failure

After a full outage no broker would rejoin, because the boot script stopped any node that couldn't find a peer. I bootstrapped one node manually, joined the rest to it and restored the configuration. The investigation also showed the same check had been producing empty 187-byte backups.
