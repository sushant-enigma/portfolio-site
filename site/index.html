Work

Things I've worked on

Moving Kafka off MSK, and the mistake I made

We moved Kafka from Amazon MSK to Strimzi, which runs Kafka on our own Kubernetes clusters. I set the new cluster to gzip compression because most of our applications already used it. I didn't check every one.

A few apps used lz4. Once traffic moved over they ran into trouble, and consumer lag kept going up. Going back halfway through wasn't a good option, so I wrote a small transcoder that let the lz4 apps keep working with the gzip messages. They caught up and the migration carried on.

Now I check every producer and consumer before I change a setting for the whole cluster.

Keeping up with 2 million meters

Readings from over 2 million meters come in through four production EKS clusters. I moved them off fixed node groups to Karpenter, with KEDA scaling the Kafka consumers on lag and HPA and VPA handling the rest.

I left some things fixed on purpose. The meter-data workloads have steady load, so they run on fixed capacity and don't get moved around.

The AWS bill

Across 22 AWS accounts the bill runs at around $50K a month, and keeping it down is part of my job. Most of the savings came from plain work: right-sizing, a node group nobody was using, old CloudWatch agents in six accounts, reserved instances for Aurora, and turning dev and stage off out of hours.

Together that's about $45K a year saved.

An old app from $2,200 to $1,300 a month

One legacy application still ran on Python 2.7 with MySQL 8 behind it, and it cost about $2,200 a month to keep running. I moved it and cut what it didn't need. It now costs about $1,300 a month.

Builds that only rebuild what changed

Every commit used to rebuild and redeploy the whole platform, which took about 30 minutes even for a one-line change. I changed the pipeline to work out which services a commit touches and build only those. Most builds now take 2 to 4 minutes.

Incidents

Things that broke

A few production problems and how I tracked them down.

It looked like the network. It wasn't.

Every service on one cluster kept losing its Postgres connection with "unexpected EOF". The database server had strict memory overcommit and no swap, so Postgres had only about 140 MB left to start new connections. One kernel setting fixed it, without a restart.

An autoscaler that starved its own consumers

A Kafka consumer group kept rebalancing and never caught up. Lag got to 20 million messages. VPA had shrunk the decoder pods from 500m CPU to about 53m, so each batch took longer than the poll timeout and Kafka kept kicking them out. I fixed the CPU at 200m and set VPA to recommend only.

An MQTT cluster that couldn't start from zero

After every broker went down at once, none of them would come back. The boot script looked for other nodes to join and stopped the broker when nobody answered, so no node could go first. I started one by hand, joined the rest to it and restored the config. The same check had also been quietly breaking our backups. They were 187 bytes each.
